## 1. 标准八步流程（大型功能）

适用于：新玩法、新系统、跨模块改动。每步有准出条件，不满足不回退、不带病推进。

### 步骤 1：需求分析（Producer + Game Designer）

- **输入**：用户 / 团队提出的原始需求。
- **动作**：
  - Producer 界定范围：这个版本做什么、不做什么、以后做什么
  - Game Designer 把需求翻译成玩家可感知的行为变化
  - 双方共同写出**可验收的标准**（怎样算做好了）
- **输出**：需求清单、范围说明、验收标准
- **准出条件**：范围与验收标准双方确认，无歧义

### 步骤 2：项目审计（Technical Lead + Gameplay Programmer）

- **输入**：步骤 1 的需求与验收标准。
- **动作**：
  - 阅读相关现有代码与项目结构，列出可复用系统
  - 分析改动影响面：哪些模块会被触碰、哪些测试会受影响
  - 识别技术债与风险点
- **输出**：代码阅读笔记、可复用系统清单、影响面分析
- **准出条件**：已实际读过相关代码（不是凭印象），改动边界清晰
- **纪律**：此步骤不可跳过。没读代码就出方案 = 盲目设计。

### 步骤 3：策划设计（Game Designer）

- **输入**：需求清单、验收标准、审计发现（技术约束）。
- **动作**：
  - 设计核心循环、规则、数值、难度曲线
  - 数值以配置表形式输出，便于程序实现与后续调平衡
  - 标注需要 QA 重点验证的体验风险点
- **输出**：设计文档、数值配置表、体验验收要点
- **准出条件**：程序能无歧义地按文档实现；边界情况有定义

### 步骤 4：技术方案（Technical Lead）

- **输入**：设计文档、审计报告。
- **动作**：
  - 模块划分与接口设计（遵守既有架构风格）
  - 性能预算分配（帧率 / 内存 / 包体 / 加载）
  - 风险预案与回滚方案
  - 技术债评估：本次引入什么、是否可接受
- **输出**：技术方案、接口定义、性能预算、风险清单
- **准出条件**：覆盖审计发现的影响面；最薄弱环节有预案

### 步骤 5：实现（Gameplay Programmer + 相关角色）

- **输入**：技术方案、设计文档、数值配置表。
- **动作**：
  - 按方案实现；遵循既有代码规范；复用已有系统
  - 编写单元 / 集成测试（逻辑与边界）
  - 处理边界情况：空值、极限值、异常输入、中断恢复
  - 自测并记录：提交前跑通验收标准中的每一条
- **输出**：功能代码、测试、自测记录、提交说明
- **准出条件**：验收标准逐条自测通过；无硬编码兜底、无被屏蔽的异常

### 步骤 6：QA 测试（QA Engineer）

- **输入**：可运行构建、验收标准、设计文档。
- **动作**：
  - 按验收标准与测试用例执行功能测试
  - 边界与异常测试：极限输入、快速连点、断网、杀进程、存档异常
  - 记录 Bug：环境、复现步骤、期望 vs 实际、严重级
- **输出**：Bug 报告、测试结果
- **准出条件**：验收标准全覆盖；无阻塞级 Bug

### 步骤 7：回归测试（QA Engineer）

- **输入**：修复后的构建、历史功能清单。
- **动作**：
  - 验证旧功能无回退（重点：本次改动的关联模块）
  - 性能对比：帧率 / 内存 / 加载时间未劣化
  - 验证修复未引入新问题
- **输出**：回归测试报告
- **准出条件**：回归通过，性能指标在预算内

### 步骤 8：文档更新（本轮涉及角色）

- **动作**：同步设计文档、技术文档、使用说明、Changelog
- **准出条件**：文档与代码一致，无过期描述

## 2. 场景流程模板

### A. 新功能全流程

```
Producer → Game Designer → Technical Lead → Programmer → QA → Build & Release
```

即标准八步流程的完整展开，用于里程碑内的新功能。

### B. Bug 快速修复

```
Technical Lead（定位根因）→ Programmer（修复 + 补测试）→ QA（验证 + 回归）
```

- 小 Bug 可压缩为：Programmer（修复 + 自测）→ QA（抽验回归）
- 任何情况下不得：只改表现层症状、删测试、吞异常

### C. 性能优化专项

```
Technical Lead（剖析数据、定目标与预算）→ Technical Artist / Programmer（优化）→ QA（验证效果与回归）
```

- 先测量后优化，无数据不优化
- 每次只改一类变量，效果可归因
- 优化后必须回归：功能没被"优化"坏

### D. 关卡 / 内容制作

```
Game Designer（规则与目标）→ Level Designer（布局与节奏）→ Programmer（工具 / 配置接入）→ QA（可通关性与难度验证）
```

- 关卡必须实际可通关（QA 跑通或自动验证）
- 难度以玩家死亡 / 卡关数据为依据调整，不凭感觉

### E. UI / 美术落地

```
UI/UX & Art Designer（信息架构与风格）→ Programmer（实现与对接）→ QA（交互与兼容性验证）
```

- 涉及 Shader / 特效 / 光照时加入 Technical Artist
- 资产先过规格检查（尺寸、数量、格式）再进入实现

### F. 版本发布冲刺

```
Producer（版本目标与范围冻结）→ Build & Release（构建与检查）→ QA（发布前回归）→ 文档与 Changelog → 发布
```

- 范围冻结后只接受阻塞级修复
- 使用第 4 节发布检查清单逐项打勾

### G. 重构 / 技术债清理

```
Technical Lead（债务评估与范围划定）→ Programmer（小步重构 + 测试护航）→ QA（全量回归）
```

- 重构不改变外部行为；行为变更走新功能流程
- 小步提交，每步可独立验证与回滚

## 3. 引擎适配说明

本 Skill 引擎无关。按项目实际引擎替换工具链即可，职责分工不变：

| 引擎 | 实现语言 | 常用测试手段 | 常用剖析工具 | 构建 / CI |
|---|---|---|---|---|
| Unity | C# | EditMode / PlayMode 测试、集成测试 | Profiler、Frame Debugger、Memory Profiler | Build Pipeline、命令行构建 + CI |
| Godot | GDScript / C# | 场景测试、单元测试 | 内置 Profiler、Monitors | 导出预设 + 命令行导出 + CI |
| Unreal | C++ / Blueprint | 自动化测试框架、功能测试 | Unreal Insights、Stat 命令 | 构建脚本 + CI |
| 自研 / Web | 按项目 | 单元测试 + 浏览器冒烟 | 浏览器性能面板 / 自研工具 | 构建脚本 + CI |

原则：无论引擎，"先读代码 → 小步实现 → 自动化验证 → 回归"的纪律一致。

## 4. 发布检查清单（Release Checklist）

Build & Release Engineer 逐项确认，QA 复核：

- [ ] 版本号符合规则，Changelog 与本次改动一致
- [ ] 干净环境可复现构建（换机器 / 清缓存后构建成功）
- [ ] 自动化检查全绿：编译、单元测试、lint、包体大小
- [ ] 目标平台配置正确（图标、权限、最低版本、横竖屏）
- [ ] 签名 / 证书 / 账号配置就绪（凭据由负责人提供，不写入代码库）
- [ ] 回归测试通过，无阻塞级 Bug
- [ ] 性能达标：帧率 / 内存 / 加载时间在预算内（目标设备实测）
- [ ] 存档兼容性：旧版本存档可正常读取或明确提示
- [ ] 回滚方案明确：可退回的上一版本与步骤已确认
- [ ] 文档齐备：使用说明、已知问题、联系方式

## 5. 模板

### Bug 报告模板

```
标题：[模块] 简述现象
环境：版本号 / 平台 / 设备
严重级：阻塞 / 严重 / 一般 / 建议
复现步骤：1. … 2. … 3. …
期望结果：……
实际结果：……
发生频率：必现 / 高频 / 偶发
关联：相关提交 / 需求 / 其他 Bug
```

### 测试用例模板

```
用例 ID / 名称
前置条件：……
步骤：1. … 2. … 3. …
预期结果：……
优先级：P0 验收标准 / P1 边界 / P2 异常
实测结果：通过 / 失败（附 Bug 编号）
```
