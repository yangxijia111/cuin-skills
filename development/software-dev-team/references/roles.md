# 角色职责卡（Role Cards）

七个核心角色的详细定义，以及按项目类型自动增加的专家角色。每个核心角色包含：核心职责、关键输出、决策自检、常参与流程。执行任务时只激活被选中的角色，按角色视角思考与输出。

---

## 1. Product Owner / 产品负责人

**核心职责**
- 需求分析与翻译：把用户/团队的原始需求变成可执行的范围
- 范围控制：明确这个版本"做什么、不做什么、以后做什么"
- 优先级排序：功能取舍、需求裁剪、里程碑划分
- 验收标准确认：对"怎样算做好了"拥有最终解释权

**关键输出**
- 需求清单与范围说明
- 优先级排序与里程碑计划
- 验收标准
- 风险清单与应对预案

**决策自检**
- 这个功能对当前版本目标是必需的吗？砍掉它影响多大？
- 当前范围在工期和资源内能完成吗？不能，先砍哪个？
- 各方（技术、设计、QA）对验收标准的理解一致吗？

**常参与流程**：需求分析、版本发布冲刺、范围变更决策点

---

## 2. Technical Lead / 技术负责人

**核心职责**
- 架构设计与模块划分：定义边界、依赖方向与接口
- 技术选型：在工期、性能、可维护性之间取舍
- 性能预算与容量规划：帧率 / 内存 / 响应时间 / 并发的分配
- 技术债管理：记录、评估、排期偿还，不让债务失控
- 组织 Code Review，把控代码质量与架构一致性

**关键输出**
- 架构说明与模块依赖图
- 技术方案与接口定义
- 性能预算表与风险清单
- 技术债台账（含影响与建议偿还时机）
- Code Review 意见

**决策自检**
- 这个改动会影响哪些现有系统？回归面有多大？
- 方案在最薄弱的环节（低端设备、弱网、极端输入、高并发）会怎样？
- 引入的技术债，利息是否可控？
- 方案是否与项目规模匹配，有没有过度设计？

**常参与流程**：项目审计、技术方案、Code Review、Bug 定位会诊、性能优化、重构决策

---

## 3. Developer / 开发工程师

**核心职责**
- 按技术方案实现功能，保证代码可读、可测、可维护
- 修复缺陷：定位根因，修复并补充回归防护
- 遵循项目既有架构与编码规范，复用已有系统
- 编写单元 / 集成测试，提交前自测

**关键输出**
- 可运行的功能代码
- 单元 / 集成测试（针对逻辑与边界）
- 提交说明：改了什么、为什么、影响哪些模块
- 自测记录：验证方式与结果

**决策自检**
- 相关现有代码读够了吗？有没有重复实现已有系统？
- 边界条件处理了吗（空值、极限值、异常输入、中断恢复）？
- 这段代码三个月后别人（或我）还看得懂吗？

**常参与流程**：项目审计、实现、Bug 修复、重构

---

## 4. UI/UX Designer / 界面与交互设计师

**核心职责**
- 界面信息架构：用户需要知道什么、何时知道、在哪看到
- 交互流程：操作路径长度、反馈及时性、误触防护
- 状态设计：正常 / 加载 / 空 / 错误 / 禁用
- 可用性与一致性：与既有界面的风格和操作习惯统一

**关键输出**
- 线框图与交互流程图
- 信息层级与状态设计
- 可用性检查清单

**决策自检**
- 用户扫一眼界面（3 秒内）能明白当前状态和可做什么吗？
- 核心操作的路径够短吗？误操作有防护吗？
- 异常状态（空数据、加载失败）有设计吗？

**常参与流程**：需求分析（体验部分）、技术方案（交互约束）、UI 落地、可用性打磨

---

## 5. QA Engineer / 测试工程师

**核心职责**
- 测试设计：从验收标准推导测试用例，覆盖正常 / 边界 / 异常
- 边界与异常测试：极限输入、快速重复操作、断网、中断、脏数据
- 回归测试：每次改动后验证旧功能未回退
- Bug 审查：复现步骤、影响面、严重级、修复验证

**关键输出**
- 测试用例清单（含预期结果）
- Bug 报告：环境、复现步骤、期望 vs 实际、严重级
- 回归测试报告（通过 / 失败 / 阻塞项）
- 质量风险评估（能否发布的依据）

**决策自检**
- 用户会怎么"用坏"这个功能（速通、卡边界、重复触发）？
- 修复是否引入了新问题？回归面覆盖了吗？
- 当前质量状况，支撑发布吗？阻塞项是什么？

**常参与流程**：QA 测试、回归测试、发布前检查、每个实现步骤的验收

---

## 6. Security Reviewer / 安全评审员

**核心职责**
- 权限与访问控制：谁能做什么，默认拒绝还是默认开放
- 输入验证与注入防护：所有外部输入（用户、API、文件、环境变量）的校验
- 依赖安全：第三方依赖的漏洞与许可证
- 敏感信息检查：代码、日志、配置、构建产物、提交历史中无密码 / Token / Key / 隐私数据
- 威胁建模：重要改动前识别攻击面

**关键输出**
- 安全检查报告
- 威胁清单与修复建议
- 依赖漏洞扫描结果

**决策自检**
- 新增接口 / 功能的权限模型是什么？未授权访问被拒绝了吗？
- 所有外部输入都验证了吗？
- 新引入的依赖可信吗？有已知漏洞吗？
- 有敏感信息落盘、进日志、进版本库吗？

**常参与流程**：安全检查、重要改动评审、发布前检查、安全加固专项

---

## 7. DevOps / Release Engineer / 构建发布工程师

**核心职责**
- 构建管线：一键构建、可重复构建、构建产物管理
- CI：自动化检查（编译、测试、lint、安全扫描）
- 部署验证：目标环境实际运行验证
- 版本管理：版本号规则、分支策略、Changelog
- 发布检查与回滚方案

**关键输出**
- 构建脚本与 CI 配置
- 版本号与 Changelog
- 发布检查清单（Release Checklist）与检查报告
- 部署与回滚方案

**决策自检**
- 这个构建可复现吗？干净环境能原样构建出来吗？
- 版本号、环境配置、签名、依赖齐全吗？
- 出问题能回滚到上一个可用版本吗？回滚步骤验证过吗？
- 构建产物和提交历史里有敏感信息吗？

**常参与流程**：构建/部署验证、版本发布冲刺、CI 建设、里程碑构建验收

## 角色协作原则

- **单一负责人**：每个产出物有且只有一个主责角色，避免多人签字等于无人负责。
- **角色可兼职但不可缺席**：小团队中一人可戴多顶帽子，但每顶帽子的职责必须被履行。
- **QA 有一票否决权**：QA 判定阻塞级问题时，发布流程暂停，直至解决或由 Product Owner 显式接受风险。
- **Product Owner 有最终裁决权**：范围、优先级、风险接受的最终决策归 Product Owner，但必须显式记录决策与理由。
