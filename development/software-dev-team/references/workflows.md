## 1. 标准九步流程（大型功能）

适用于：新需求、新系统、跨模块改动。每步有准出条件，不满足不回退、不带病推进。

### 步骤 1：需求分析（Product Owner）

- **输入**：用户 / 团队提出的原始需求。
- **动作**：
  - 界定范围：这个版本做什么、不做什么、以后做什么
  - 拆解需求并排优先级
  - 与相关方共同写出**可验收的标准**（怎样算做好了）
- **输出**：需求清单、范围说明、验收标准
- **准出条件**：范围与验收标准明确无歧义，优先级清晰

### 步骤 2：项目审计（Technical Lead + Developer）

- **输入**：步骤 1 的需求与验收标准。
- **动作**：
  - 阅读相关现有代码与项目结构，列出可复用系统
  - 分析改动影响面：哪些模块会被触碰、哪些测试会受影响
  - 识别技术债与风险点
- **输出**：代码阅读笔记、可复用系统清单、影响面分析
- **准出条件**：已实际读过相关代码（不是凭印象），改动边界清晰
- **纪律**：此步骤不可跳过。没读代码就出方案 = 盲目设计。

### 步骤 3：技术方案（Technical Lead + 专家角色）

- **输入**：需求清单、验收标准、审计发现（技术约束）。
- **动作**：
  - 模块划分与接口设计（遵守既有架构风格）
  - 技术选型：工期、性能、可维护性之间取舍
  - 性能预算分配（帧率 / 内存 / 响应时间 / 并发）
  - 风险预案与回滚方案
  - 技术债评估：本次引入什么、是否可接受
- **输出**：技术方案、接口定义、性能预算、风险清单
- **准出条件**：覆盖审计发现的影响面；最薄弱环节有预案；方案规模与项目匹配

### 步骤 4：实现（Developer + 专家角色）

- **输入**：技术方案、验收标准。
- **动作**：
  - 按方案实现；遵循既有代码规范；复用已有系统
  - 编写单元 / 集成测试（逻辑与边界）
  - 处理边界情况：空值、极限值、异常输入、中断恢复
  - 自测并记录：提交前跑通验收标准中的每一条
- **输出**：功能代码、测试、自测记录、提交说明
- **准出条件**：验收标准逐条自测通过；无硬编码兜底、无被屏蔽的异常

### 步骤 5：Code Review（Technical Lead + 相关角色）

- **输入**：可审查的变更（提交 / PR / 差异）。
- **动作**：按以下维度逐项审查，提出意见并跟踪修改：
  - 正确性：逻辑、边界、错误处理
  - 安全：权限、输入验证、敏感信息
  - 性能：热点路径、复杂度、资源占用
  - 规范：编码规范、命名、注释
  - 架构：与既有设计一致性、模块边界
  - 测试：覆盖是否充分，边界是否有用例
- **输出**：审查意见、修改记录
- **准出条件**：无阻塞级问题；意见已处理或有明确理由保留

### 步骤 6：QA 测试（QA Engineer）

- **输入**：可运行构建、验收标准、测试用例。
- **动作**：
  - 按验收标准与测试用例执行功能测试
  - 边界与异常测试：极限输入、快速重复操作、断网、中断、脏数据
  - 记录 Bug：环境、复现步骤、期望 vs 实际、严重级
- **输出**：Bug 报告、测试结果
- **准出条件**：验收标准全覆盖；无阻塞级 Bug

### 步骤 7：安全检查（Security Reviewer）

- **输入**：变更内容、部署形态。
- **动作**：
  - 权限与访问控制检查
  - 输入验证与注入防护检查
  - 依赖漏洞扫描
  - 敏感信息扫描：代码、日志、配置、构建产物、提交历史
- **输出**：安全检查报告
- **准出条件**：无高危未处理项；中危项有处置决定

### 步骤 8：构建/部署验证（DevOps / Release Engineer）

- **输入**：通过 QA 与安全检查的代码。
- **动作**：
  - 干净环境构建，确认可复现
  - CI 自动化检查全绿（编译、测试、lint、安全扫描）
  - 目标环境部署并实际运行验证
  - 确认版本号与 Changelog
- **输出**：构建报告、部署验证记录、Changelog
- **准出条件**：构建可复现；目标环境运行正常；回滚方案明确

### 步骤 9：文档更新（本轮涉及角色）

- **动作**：同步需求文档、设计文档、技术文档、使用说明、Changelog
- **准出条件**：文档与代码一致，无过期描述

## 2. 场景流程模板

### A. 新功能全流程

```
Product Owner → Technical Lead → Specialist/Developer → Code Reviewer → QA → Security → Release
```

即标准九步流程的完整展开，用于里程碑内的新功能。

### B. Bug 快速修复

```
Technical Lead（定位根因）→ Developer（修复 + 补测试）→ QA（验证 + 回归）
```

- 小 Bug 可压缩为：Developer（修复 + 自测）→ QA（抽验回归）
- 任何情况下不得：只改表现层症状、删测试、吞异常

### C. 性能优化专项

```
Technical Lead（测量数据、定目标与预算）→ Developer/Specialist（优化）→ QA（验证效果与回归）
```

- 先测量后优化，无数据不优化
- 每次只改一类变量，效果可归因
- 优化后必须回归：功能没被"优化"坏

### D. UI/UX 落地

```
UI/UX Designer（信息架构与交互）→ Developer（实现）→ QA（交互与兼容性验证）
```

- 资产 / 设计稿先过规格检查再进入实现
- 异常状态（空、加载、错误）必须一并验证

### E. 安全加固专项

```
Security Reviewer（威胁建模与检查）→ Developer（修复）→ Security（复验）→ QA（回归）
```

- 先识别攻击面，再动手修复
- 修复后必须复验 + 回归，防止"修出"新问题

### F. 版本发布冲刺

```
Product Owner（版本目标与范围冻结）→ DevOps（构建与检查）→ QA（发布前回归）→ Security（发布前检查）→ 文档与 Changelog → 发布
```

- 范围冻结后只接受阻塞级修复
- 使用第 5 节发布检查清单逐项打勾

### G. 重构 / 技术债清理

```
Technical Lead（债务评估与范围划定）→ Developer（小步重构 + 测试护航）→ QA（全量回归）
```

- 重构不改变外部行为；行为变更走新功能流程
- 小步提交，每步可独立验证与回滚

### H. 依赖升级

```
Technical Lead（影响评估）→ Developer（升级适配）→ QA（回归）→ Security（漏洞扫描）
```

- 升级前先评估破坏性变更与影响面
- 锁文件 / 版本号同步更新，保持构建可复现

## 3. 小任务简化规则

小任务（小 Bug、小调整、配置修改、文案修改）走简化流程：

```
项目审计（读代码）→ 实现 → 验证 → 简述总结
```

- **保留三段硬核**：读代码、实现、验证。
- **可跳过**：需求文档、技术方案、正式测试报告。
- **仍须遵守**：十二条工作规则全部适用。验证方式可以轻量（自测 + 抽验），但不得为零。

## 4. 项目类型适配说明

本 Skill 与项目类型无关。按项目实际技术栈替换工具链即可，职责分工与流程纪律不变：

| 项目类型 | 常用测试手段 | 常用检查工具 | 构建 / 部署 |
|---|---|---|---|
| Web | 单元测试、E2E、浏览器冒烟 | lint、类型检查、依赖扫描 | 构建脚本 + CI |
| 小程序 | 单元测试、模拟器验证、真机预览 | 平台规范检查 | 平台工具链 |
| 移动 App | 单元 / UI 测试、真机验证 | lint、依赖扫描 | Gradle / Xcode + CI |
| 后端服务 | 单元 / 集成测试、契约测试 | lint、SAST、依赖扫描 | 容器构建 + CI |
| CLI | 单元测试、跨平台冒烟 | lint、跨平台矩阵 | 打包脚本 + CI |
| AI 应用 | 评估集、冒烟测试 | Prompt / 输出检查、依赖扫描 | 构建 + CI |

原则：无论技术栈，"先读代码 → 小步实现 → 验证 → 回归"的纪律一致。

## 5. 发布检查清单（Release Checklist）

DevOps / Release Engineer 逐项确认，QA 与 Security Reviewer 复核：

- [ ] 版本号符合规则，Changelog 与本次改动一致
- [ ] 干净环境可复现构建（清缓存 / 换机器后构建成功）
- [ ] 自动化检查全绿：编译、测试、lint、安全扫描
- [ ] 目标环境配置正确（环境变量、域名、证书、权限）
- [ ] 依赖已固定版本，无已知高危漏洞
- [ ] QA 回归通过，无阻塞级 Bug
- [ ] 安全检查通过，无高危未处理项
- [ ] 性能 / 容量指标达标（如适用）
- [ ] 数据兼容性验证：旧数据可正常读写或明确提示（如涉及存储 / Schema 变更）
- [ ] 回滚方案明确：可退回的上一版本与步骤已确认
- [ ] 文档齐备：使用说明、已知问题、运维联系方式
- [ ] 构建产物与提交历史中无敏感信息

## 6. 模板

### Bug 报告模板

```
标题：[模块] 简述现象
环境：版本号 / 平台 / 设备
严重级：阻塞 / 严重 / 一般 / 建议
复现步骤：1. … 2. … 3. …
期望结果：……
实际结果：……
发生频率：必现 / 高频 / 偶发
关联：相关提交 / 需求 / 其他 Bug
```

### 测试用例模板

```
用例 ID / 名称
前置条件：……
步骤：1. … 2. … 3. …
预期结果：……
优先级：P0 验收标准 / P1 边界 / P2 异常
实测结果：通过 / 失败（附 Bug 编号）
```

### 安全检查报告模板

```
检查对象：变更内容 / 版本号
检查人角色：Security Reviewer
检查项：
- 权限与访问控制：……（结论）
- 输入验证与注入防护：……（结论）
- 敏感信息：代码 / 日志 / 配置 / 构建产物中无密码、Token、Key、隐私数据（结论）
- 依赖安全：无已知高危漏洞（结论，附扫描结果）
- 安全配置：……（结论）
总体结论：通过 / 有条件通过（附处置项）/ 不通过（附阻塞项）
```
